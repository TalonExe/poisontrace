# Research objectives review

Reviewed 2026-11-10 against the current working tree, including untracked canonical source. No application changes or live-provider calls were made. Existing work and local experiment records were preserved.

## Assessment

All five objectives are **partially fulfilled**. PoisonTrace has a useful experiment interface, provider adapters, synthetic metadata attacks, policy checks, persistence and repeat execution. It does not yet implement the PDF's end-to-end sandboxed MCP SOC benchmark. Its current marker measurements and historical runs do not demonstrate security effectiveness, preserved SOC utility or comparative model performance.

The largest mismatch is substantive, not organizational. A model produces its final recommendation before a gateway allows or denies a proposed call. No tool actually retrieves evidence, and no tool result returns to the model. A marker in that completion determines attack success. The research instead requires evidence-driven SOC investigations and observable policy or investigation failures.

## Sources, page convention and review method

Primary research source: `../Havyn Liew Investigation Report.pdf`, 118 PDF pages, 2,775,223 bytes. SHA-256 verified as `90D3949DA9A402E97A6834F0169FA94096EA1BC1061C5347025D215717F9C82F`.

Page references below use the one-based PDF page position. The zero-based PDF index is that number minus one. The inspected pages have no separate printed page-number footer. The contents lists the objectives at 15, scope at 16 and interviewer sheet at 72, matching those PDF positions. Thus `p15 / index14` identifies the objectives page without inventing a printed folio. Complete relevant pages were extracted, and rendered pages 15-22, 60, 72 and 91-92 were visually inspected, including all bullet continuations. Extraction of the remaining document checked the abstract, technical design, methodology, interview mapping and conclusion for additional commitments.

Section 1.4 on p15 contains five explicit objectives. The interviewer sheet on p72 repeats them with two additions: O1 includes a focused threat model, and O4 names metadata scanning, integrity checking and LLM-based intent alignment. Both versions are assessed. Section 1.5 on pp16-21 supplies concrete acceptance requirements. The project implications on pp91-92 clarify policy outcomes and trace reproducibility. The future research discussion on pp95-96 is not automatically a mandatory implementation backlog. No separate numbered research-question list was found; interview questions are data-gathering instruments, not additional system objectives.

The PDF describes an investigation and proposed system. Pages 54 and 94 explicitly distinguish intended capability from experimentally validated effectiveness. Its literature benchmark percentages and interview findings are not PoisonTrace experiment results. Scrum in pp63-69 is the development method, while interviews and thematic analysis in pp70-92 inform requirements. Those interviews do not replace the promised system and usability evaluation.

Read repository instructions, context, glossary, implementation brief, architecture/rules, current status and ADRs. Traced current backend, scenarios, provider prompts, dashboard, tests and available artifacts. Supporting source-level findings and safe database aggregates are in [implementation evidence](research/IMPLEMENTATION_REVIEW_EVIDENCE.md).

Verdicts have these meanings: `fulfilled` means the requirement exists at the stated scope; `partially fulfilled` means only part exists; `not implemented` means the inspected code has no corresponding capability; `not yet demonstrated` means research evidence is insufficient. Tests prove implementation behavior, not model effectiveness.

## Measurement findings that change the verdict

1. Marker detection is useful evidence that an instruction influenced output. It does not establish disclosure, unauthorized tool use or wrong triage. Conversely, a meaningful violation without the marker scores as attack failure. Tests explicitly preserve this behavior. The glossary also calls benign task success marker absence, while execution additionally requires a permitted call or fallback and exact recommendation equality. Update definitions together when the measurement is redesigned.
2. Defended marker absence is reported as defense blocking even when no control blocked anything. Clean task failure is counted as a false positive regardless of cause. A marker-absent result can be labeled `Blocked`, and `application/runs.py:112` labels it `Benign success` even if task outcome is failed. These labels overstate what the evidence proves.
3. A blocked call can coexist with successful model manipulation because the completion precedes enforcement. `safe_fallback_used` changes the task-success condition but `recommendation_created` still records the original decision; it does not perform a new evidence-based investigation or necessarily replace the recommendation.
4. Clean mode is not an input transformation. An offline in-memory probe using runtime scenario 002 confirmed poisoned metadata reaches the model in clean, poisoned and defended modes. With a deterministic marker-emitting model, clean and defended both recorded attack success plus a blocked call; poisoned recorded attack success plus simulated execution. This probe used no provider and persisted no application data.
5. Additional pure-metric probes confirmed a defended wrong-task/no-marker result produces blocking rate 1.0, and a clean wrong-task result produces false-positive rate 1.0. These are counterexamples to interpreting the present fields as measured prevention and defensive false positives.

| gemini-3.5-flash-lite | poisoned | 37 | 8 | 0 |

These are exploratory historical records, not a balanced research dataset or independently authenticated provider transcripts. Only 35 of 42 runs have an agent-output event. Mutable inputs, missing snapshots, no second model group and unequal conditions prevent a defensible causal comparison. Neither 8/37 versus 1/4 nor the zero stored error flags establish defense effectiveness or reliability. All recorded benign-task successes are false; the data do not demonstrate preserved SOC utility. Scratch architecture comparison databases are not research experiments.

## Decisions to settle before the evaluation phase

The review can establish gaps without these answers. They affect the eventual study protocol:

1. Should the expanded p72 O4 wording make an LLM-based intent validator mandatory, or will the final report narrow and justify the selected defense set? This review treats it as a stated requirement until revised.
2. Which model versions, per-condition repetition count and API budget are available? The PDF requires multiple models and repeats but sets no numerical sampling target.
3. Which participant group is realistically accessible for the p19 usability study? Professional access is qualified by availability, but student and professional evidence must remain distinct.
